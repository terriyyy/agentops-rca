# Run 级原因分析与任务检查：调研与方案

日期：2026-09-30。本轮仅研究和设计，没有修改产品代码、API、模型提示或持久化数据。当前 Trace + Selected Event 骨架、Run-centric 与事实语义继续保留。

## 推荐结论

首屏 Trace 工具栏提供明确的 Run 级主操作“分析失败原因（RCA）”，失败事实旁提供同一个操作的上下文入口。底部保留限高、可调节、可收起的工作面板，改为“原因分析 / 任务检查”两种用户意图。技术资料与分析记录进入次级菜单，避免与 RCA 和任务结果占据同等权重。

入口进入准备/预览流程，绝不等于立刻调用模型。Run 的分析对象明确写“本次运行”，右侧事件详情仍只服务选中事件。不添加第三个常驻列、聊天机器人、调查实体或新报告页。

## 当前产品的问题及代码依据

1. **术语先于任务。** “根因假设”“独立验收”“HGT定位”“analyst”要求新用户先理解原理。用户需要知道为什么失败、任务是否做对、下一步看哪条记录。
2. **入口偏弱且技术化。** 主操作在底部 DiagnosisControls 的右侧，按钮分 HGT 和 RCA 预览，且后者因前置条件禁用。普通用户无法自然判断第一步。
3. **报告原文堆叠。** DiagnosisPanel 同屏铺 `summary/boundary/guidance/verification_suggestion`，重复出现状态、待验证说明和警告。用户要从长文自行抽取结论、证据与下一步。
4. **证据名称不可扫读。** 持久化 RCA 引用 label 为 `事件 <短ID>`；UI只显示前三个引用，无法从标签判断哪个是调用、哪个是失败返回。
5. **计数有歧义。** “根因假设 5”实际来自 `report_count`，包含定位、模型分析、历史报告；不是五个根因，也不是五次验证。
6. **检查语义不自然。** OutcomePanel 同屏多次显示“验收未通过”，中间是 source 与抽象 basis；没有优先说明检查了什么、在哪项失败。
7. **空间与内容量不匹配。** 所有 Tab 复用同一 dockHeight（默认244px，可扩大），只有一条检查或三个折叠标题也保留大块空白。技术资料在切换和折叠之间增加一层理解成本。
8. **生成内容本身不受短文约束。** analyst_context 只要求简体中文和 specific hypothesis，没有字数/短句要求；单靠 CSS、截断或硬拆分不能保证清晰，也可能丢掉否定和不确定性。

成熟产品确实使用 Tabs 和折叠。我们的问题是三者等权、诊断入口弱、先解释术语再展示结果、把报告全文直接当工作面板。

## RCA 入口位置比较

| 位置 | 好处 | 风险 | 结论 |
| --- | --- | --- | --- |
| 首屏 Trace 工具栏的 Run 级操作 | 一眼能发现；实时/结束状态均可明确；保持当前工作对象 | 需要写“分析本次运行”，避免误以为只分析搜索结果 | 推荐主入口 |
| 失败事实/验收失败项旁 | 用户刚发现异常就能进入分析 | 只有失败上下文时能出现，不能作为唯一入口 | 推荐同操作的次级入口 |
| 右侧选中 Event Detail | 靠近当前证据 | 容易让用户误认为诊断只针对选中事件，抢占输入/输出 | 只提供轻量关联，不放整份 Run 分析 |
| 当前底部唯一入口 | 改动少 | 可收起、易忽略；亮点和算法前置条件同时被藏住 | 不推荐作为唯一入口 |
| 独立侧栏导航/独立 RCA 页面 | 单项能力曝光高 | 脱离 Run/Trace、证据往返；增加业务结构 | 本轮不采用 |
| 第三个常驻诊断列 | 原因一直可见 | 1366px 下挤占 Trace/Selected Event，信息空状态也占宽 | 本轮不采用 |

## 推荐页面结构

```text
现有 Run Header + 四类独立状态

Execution Trace   搜索 / 筛选 / 定位失败       [分析失败原因（RCA）]
明确失败时：工具失败 / 任务检查未通过           [查看原因分析]

┌────────────────────────────────┬─────────────────────────┐
│ 现有 Span/Event + Timeline      │ 现有 Selected Event     │
│ 保持选择、真实时间、证据定位    │ Input / Output / Error  │
└────────────────────────────────┴─────────────────────────┘

原因分析   任务检查 · 未通过        分析记录(5)  更多资料 …   收起
┌────────────────────────────────┬─────────────────────────┐
│ 可能原因（待验证）              │ 相关证据               │
│ 1–2句；证据不足时明确说明       │ #05 run_tests · 调用   │
│ 下一步该检查什么                │ #06 run_tests · 返回   │
│ 尚不能确定：具体缺口            │ 点击定位 Span / 原件   │
└────────────────────────────────┴─────────────────────────┘
```

上述两列仅是现有底部面板内部内容。宽度不足回退一列；不增加主工作区第三列。“分析记录(5)”说明五份报告而非根因数量。

## 原因分析：短结论 + 可核对证据

默认内容只回答四件事：

- **发生了什么：** 从事件/检查事实提取一句话，不把模型主张当事实。
- **可能为什么：** 使用已有报告摘要，保留条件和不确定性；待验证标记只出现一次。
- **依据是什么：** 可读证据行，注明事件/工具/返回或检查来源；每条保持原始 evidence_id/event_id。
- **下一步查什么：** 最相关检查建议，明确未执行；不能提供实际可执行的“运行测试”按钮。

针对截图的易懂示例（设计文案示意，非新增诊断结论）：

```text
发生了什么
run_tests 返回 AssertionError: addition failed。

可能原因 · 待验证
现有分析把问题指向加法实现或调用路径。
还不能确定具体是哪段代码或输入导致。

相关证据
#05 run_tests · 调用参数     #06 run_tests · 失败返回

下一步检查
核对 add(2, 3) == 5 的断言、输入与实际返回值。
检查尚未执行；当前记录未提供实际返回值。
```

截图中的当前摘要主要重复了“加法相关断言失败”，并未缩小到具体代码/参数。界面必须允许“尚不能确定具体原因”成为有效分析结果。若要更明确定位，还需要实际返回值和代码/调用上下文；不能靠更强语气的改写补齐证据。

禁止仅凭这条断言写“加法代码写错了”“把减号改为加号”“根因已确认”。禁止伪造因果图、可校准置信度或已完成分析步骤。当前 `evidence_chain` 为 ID 引用，不是充分的自然语言因果路径。

`boundary` 中会影响操作的限制显示一条；剩余边界/建议/完整原文进入按需详情。不要默认同时铺全部。完整报告可在本面板扩展/浮层读取，关闭返回相同 Trace 选择和滚动位置。

## 任务检查：是否达标与为什么失败分开

主标签改为“任务检查”，首次可见短说明“根据上报的测试或规则，判断任务是否达标”。“独立验收”保留技术术语说明，含义是独立于模型解释，不是平台另跑了一次测试。

默认采用紧凑检查行，按现有记录展示状态、检查依据、来源、原件入口；展开失败项显示原始断言/日志，成功项可收起。Run级结论继续完全使用现有后端投影，不新做前端聚合。

```text
任务检查 · 未通过
✕ python-assertion    add(2, 3) == 5
  记录：assertion failed
  来源：接入脚本上报  [查看检查记录]
  实际返回值：当前记录未提供
```

特殊情况：

- 缺记录：任务是否达标仍未知，显示“尚无检查结果”，不写“没问题”。
- 历史导入：历史检查记录，本平台未重新执行。
- 报告/遥测结果：明确“报告提供的任务结果”，不冒称独立测试。
- 冲突：显示“检查记录存在冲突，任务结果未知”，并列来源，不静默取最近。
- 任务检查通过：只说明这次检查通过；不能使根因假设变为已证实。
- 只有检查失败：照样显示分析入口，不伪造工具错误事件。

## 技术资料与分析记录

“技术详情”取消主路径的平级 Tab，进入“更多资料”菜单/按需抽屉。保留所有 HGT/RCA 作业、算法/模型版本、输入/发送内容快照、SHA-256、原始输出、provenance 和原件入口。

当前作业失败原因在主分析区解释，如“模型调用失败，保留上一份分析”；工程栈/详细日志进入资料。历史分析以日期、类型、状态和来源组成紧凑行，选中某份才展示报告。旧报告与新作业失败可同时存在。

JSON/哈希默认折叠合理。没有数据的资料不打开大面板，显示明确空状态；只读资料不获得自动执行权限。

## 状态与操作

| 真实状态 | 首屏操作/状态 | 工作面板 |
| --- | --- | --- |
| running / capture pending | 分析入口可见且解释“运行结束、采集完整后可分析” | 轻量状态；已存在的结果保持原来源，不自动调用 |
| 已结束，未定位 | “分析失败原因”打开准备页 | 明确需要先本机定位，按钮“开始定位（本机）”；点击后才建现有HGT作业 |
| 定位作业运行中 | “正在定位异常” | 只显示真实job阶段，不造进度百分比 |
| 只有定位结果 | “继续分析原因” | 显示定位线索；RCA预览前提如实，不能叫已找到根因 |
| 可生成发送预览 | “预览并分析原因” | 模型、数据范围、实际发送内容；明确人工确认才调用 |
| analyst正在运行 | “正在分析” | 真实作业状态，可取消；旧报告可保留 |
| 已有RCA假设 | “查看原因分析” | 当前选定报告、待验证短结论、相关证据、下一步检查 |
| 只有历史报告 | “查看历史分析”及重新分析入口 | 标注来源；不声称平台本次已分析 |
| 证据不足 | 保留分析入口及明确限制 | 写清仍不能确定什么，不把失败步骤直接升级成根因 |
| 最近作业失败 | “分析未完成” | 错误说明、旧报告、手动重试；不自动重试付费调用 |

面板保留自滚动和收起能力。失败且用户尚未交互时展示短分析/检查摘要；用户切换、缩放、选择后后台刷新不夺走其视图。任务检查只有一项时按内容量压缩（建议约140–200px），原因区约220–280px，始终保证主要Trace区域可用，不固定留下大片空盒子。

| 当前 | 普通界面 | 说明 |

## 实施分层（后续获准时）

1. **前端入口与措辞：** 同一个Run级动作、用户意图标签、报告数修正、技术资料降级、按内容量面板高度。验收：新用户首屏能找到分析入口；点击入口不调用模型。
2. **结果与证据阅读：** 复用summary/findings/guidance/verification_suggestion/boundary/outcomes；用event_id关联工具名、位置、调用/返回；保留完整原文及未解析引用。验收：无新增事实/因果结论，任何证据能追溯原件，检查状态不受分析变化影响。
3. **准备/预览流程：** 复用当前作业接口，明确HGT前置、模型配置、采集完整性、实际发送内容及确认。验收：cancel不发送；只有确认POST analyst-jobs；重试和截断如实说明。
4. **可选内容契约优化：** 若真实模型输出仍长，再单独调整新报告的简短摘要与不确定性格式；不修改历史原件、不另调模型做展示摘要。当前不承诺仅前端能可靠重写所有历史自由文本。

不新增后端命令执行、修复/PR、付费自动诊断、诊断置信度、Hypothesis Tree 或业务实体。本轮方案已完成；是否实施留给后续开发请求。
