# V0.3 续阶段：AgentTether analyst RCA 接入计划

状态：complete（2026-09-26）。已实现并按 [analyst RCA 验收说明](v0.3-analyst-validation.md) 验证。现有 V0.3 离线 HGT 保持独立；完整 RCA 的产品含义是“有证据引用的根因假设及下一步验证建议”，不等于已证实根因或自动修复。

## 目标与验收边界

已结束且采集完整的一次 Run，在用户明确点击后，以其**固定快照 + 同快照的真实 HGT 定位**调用 AgentTether 原有 `LLMRecoveryAnalyst`，形成可追溯的分析报告。HGT 离线按钮、历史报告与独立任务验收保持各自语义。首版不调用 repair、不修改被监控代码、不自动重试，也不把语言模型自报的 confidence 当校准概率。

默认只对本地确定性测试 Agent 的失败 Run 做真实服务验收。真实模型 Agent 兼容性及私有历史大样例的算法效果继续单独评估。功能开发期间优先用假的模型传输验证逻辑；真实 ChatAnywhere 请求仅在明确的“运行 RCA”操作或一次受控验收中发生。

## 已确认的接入条件

- 平台现有 `DiagnosisManager`/`diagnosis_jobs` 负责单作业、幂等、取消、超时、重启收尾；`DiagnosisReport` 可与历史及 HGT 报告并存。
- `diagnosis_worker.py` 主动封锁 socket 网络，主服务的子进程环境白名单不含模型密钥。因此需要**新增独立的 analyst 执行模式**；绝不解除离线 HGT worker 的网络限制。
- 上游 `LLMRecoveryAnalyst.analyze_to_plan()` 接收选中子轨迹、候选转换和结构化证据，返回计划及元数据；原 `RecoveryEngine` 在 analyst 失败时可能退回 HGT 计划，其 `verification.ok` 仅证明 bundle 可用。平台必须单独判定 analyst 是否成功，不能将 fallback 记为完整 RCA。
- 本机 `.env` 中的 `OPS_OPENAI_API_BASE_URL`、`OPS_OPENAI_API_KEY`、`OPS_OPENAI_MODEL` 已齐备；主服务只检查 Key 是否存在，不保存 Key 内容，analyst 子进程在实际请求时加载它。能力接口只返回是否配置。密钥不进入作业配置 JSON、数据库、前端或日志。

## 实施阶段

### 1. 固定数据契约和输入预览

新 analyst 作业使用 `mode=analyst_rca`，记录 `hgt_diagnosis_id`、原 Run 的 `input_snapshot_hash`、HGT 结果哈希、adapter/source/weight/manifest 版本、模型名、提示内容 SHA-256、时间与状态。先要求同一 Run 有一份成功的真实 HGT 报告；若来源、快照或哈希不一致则拒绝。保留原始输入快照和 HGT 报告，不以最新可变页面状态重组输入。

从 HGT `selected_localizations` 构造 `CriticalSubtrajectory` 与 `CriticalTransition`，传给原 `LLMRecoveryAnalyst`；明确这是平台的 HGT + analyst 适配流程，不声称与原 `generate_report` 全管线逐字段等同。若无可验证定位或转换 ID 映射，停止在 `insufficient_evidence`，不填充想象的候选。

只发送候选转换及必要上下文；排除 verification 的预期答案、运行环境变量与令牌，先按现有采集脱敏规则加一道发送前脱敏。限制转换数、每段文字、整个请求字节数；超限时拒绝或给出可见的截断说明。页面展示**即将发送的脱敏片段及大小**，请求携带预览哈希，服务端再次计算一致才提交。此预览也是成本与隐私边界。

### 2. 凭据、能力与网络进程

离线 HGT 仍执行 `block_network()`。新增仅供 analyst 模式运行的子进程，读取固定位置的本地 `.env`；使用 HTTPS、预期 ChatAnywhere 主机和预期 `/v1` 接口，拒绝请求体中的任意 URL 或路径。先做本地配置检查，不在每次页面加载时探测服务或产生模型调用。能力至少区分 `unconfigured`、`configured`、`last_call_failed` 与 `last_call_succeeded`，并注明 HGT 独立状态。

上游 analyst 的 JSON 解析与计划结构继续复用；平台以封装/子类控制传输参数，不修改外部源码。适配层在调用前限制输入，在传输层限制输出 token、超时和**单次请求且不自动重试**；先用假的模型传输验证 `gpt-5.6-luna` 所需参数，再做一次真实测试。失败原因向 UI 给出受控类别（鉴权、权限、配额、超时、无效 JSON 等），日志删除 Key 和可疑头信息。取消可以终止本机 worker；若服务商已收到请求，调用可能已计费，页面需明确提示。

### 3. 作业与报告语义

沿用 SQLite 作业队列及全局单并发。相同 `(run_id, request_id)` 仅有一个作业；重启后的 `interrupted` 不自动重发，避免重复计费。新请求需要新的 request_id 和显式点击。超时、取消或服务关闭后的晚到结果不能发布成功报告。

analyst 输出必须校验：结构化字段完整、转折点 transition ID 存在于本次固定子轨迹、证据链可映射到本次快照的事件或标为 `unresolved`。不能只凭可解析 JSON 判定成功；缺少可验证引用时标记 `analysis_incomplete` 或降级，不以“已证实根因”展示。保存模型回复、报告、输入与来源版本在本地被忽略的存储中，保持历史报告/HGT 报告可独立查看。`RecoveryPlan.verification` 是**建议执行的检查**，绝不能写入 `Outcome` 或覆盖既有验收。

报告增加 `mode=analyst_rca`、analyst 结果状态、根因假设、证据引用、建议操作、建议验证、适用边界、来源模型与版本、请求/响应摘要、可用时的 token 使用量。密钥、Authorization、原始 HTTP 头永不持久化；模型自报置信度仅作为未经校准的模型字段保留。

### 4. 页面与操作说明

在“诊断报告”页保留“运行 HGT 定位”，当同快照 HGT 已成功且 analyst 已配置时显示“查看发送内容”与“运行 RCA”。按钮文案和状态区分离线 HGT 与联网 analyst；显示预计发送范围、已记录的模型名、一次调用提示、进度、取消/重试条件。报告分区展示 HGT 候选、analyst 假设、可点击原始证据、待执行的验证建议和独立验收结果。来源页显示“配置就绪”不等于“最近调用成功”。

### 5. 验收顺序

1. 不联网的适配测试：固定 HGT 输出映射、快照与提示哈希、脱敏/截断、缺候选、证据引用越界及历史结果不变。
2. 模拟模型测试：完整 JSON、非 JSON、字段缺失、伪造 transition ID、401/403/429、超时、取消、重启、重复 request_id；检查失败时不会生成假报告或重发计费请求。
3. 端到端浏览器检查：预览 → 明确触发 → 等待 → 报告证据跳转 → 刷新恢复；HGT 单独路径回归。
4. 一次小范围真实 ChatAnywhere 验收：确定性的**合成失败**轨迹，记录模型/响应状态、可用的 token 用量和证据解析率；人工比对已知故障。不以一次成功推论诊断准确率。
5. 运行现有后端/浏览器回归、前端构建；核查 `.env`、模型原文、私有日志、权重未进入 Git，更新 README 和数据契约。

完成标准：点击 RCA 才产生联网请求；一个失败案例有可追溯、明确标为“假设”的 analyst 解释；非法或无证据的回复不伪装成功；取消/重启/重试语义和调用成本清楚；离线 HGT 与既有验收结果不受影响。真实模型 Agent 和诊断效果评测仍另列后续任务。
