# 前端体验与用量指标调研建议

日期：2026-10-04。性质：产品建议和数据审查，不是实施计划。本轮未修改应用代码、启动 Agent、运行 HGT 或调用模型。

## 1. 结论与 skill 的适用方式

建议保留 Run-centric、共享时间轴、选中步骤详情及 Run 级原因分析／任务检查，增补可追溯、可点击的运行用量摘要和少量首页概览指标。重点是让用户从数字进入具体步骤、失败或检查依据。

用户指定的 design-taste-frontend 技能在第 13 节明确将密集产品 UI、Dashboard 和数据表列为范围外。因此本轮参考其“先审查、保留现有架构、克制视觉、真实数据”的原则，产品交互依据成熟观测工具；不套用营销网站的大标题、动效、图片、卡片网格，也不因此更换现有组件库。

方向：浅色、高密度开发者工具；局部演进，不重新设计信息架构。纯白底、类型实心条、失败／选中／引用的区分是已经完成的基础，不列为新功能。

## 3. 当前实现中值得优化的具体问题

1. 首页有较大的常驻接入说明和演示入口。首次使用有价值，重复使用时会占据实时运行和待处理事项的首屏位置。首次接入指导与日常紧凑入口应有不同展示状态，但不更换首页主任务。
2. Run 的工具条和事件列表已经像调试工具，但用户仍难以迅速知道本轮用了几次模型、多少 Token、哪些步骤最慢。
3. 目前 Token 展示只读取 `output.usage.total_tokens`。真实 LangChain 记录的 `output.usage_metadata` 尚未进入该展示逻辑，输入／输出拆分也未展示。
4. LLM 请求与响应目前保留为独立事件；若直接统计 llm 事件数，会把 7 次调用显示成 14 次。不能拿事件数当调用量。
5. 默认完整事件列表中大量 LOG 会淹没工具和模型步骤。需要更易理解的“执行步骤／全部事件”查看方式，原始日志仍保留并可访问。
6. 筛选后右侧可能仍保留不在当前列表中的选中事件；已有“定位并显示”提示，但仍需让用户清楚区分“当前筛选”和“固定选中的调查对象”。不能为了外观自动清掉证据定位。
7. 底部面板已经可收起、自身滚动、可调整高度，且技术资料已移入按需查看。应保留；不把这些已经实现的能力再次列为待新增。当前所有已结束 Run 默认展开底部面板，成功且无分析的 Run 会为缺少内容的面板留出较多空间，可进一步按明确状态调整默认展示。
8. 基础字号为 15px，但部分工具栏统计、时间导航、状态等局部为 10–12px；是局部可读性问题，不宜全页等比放大。模型／工具名称、结果和主要操作宜优先保证阅读。
9. 当前 `/overview?limit=20` 返回三组有限的运行列表，没有全量时间窗口统计。前端列表长度不是全局正在运行数、失败率或总用量。

## 4. 可以增加哪些指标

“流量”应先明确为运行量或模型调用量；网络字节吞吐尚无采集依据。

| 指标 | 建议位置与展示 | 点击后做什么 | 当前数据与新增工作 |
| --- | --- | --- | --- |
| 当前正在运行 | 首页概览中的紧凑数字 | 聚焦正在运行列表 | 已有执行状态；全局计数需查询接口，不能取 limit 列表长度 |
| 需要处理的 Run | 首页概览 | 筛选执行异常、任务检查未通过等，保留具体理由 | 已有 attention 投影；需全量去重计数，排除演示可选 |
| 运行量 | 首页选定时间范围的趋势条 | 点击时间桶查看该时间范围内的 Run | 已有运行记录；需聚合 API 及可靠来源时间口径 |
| 模型调用量 | Run 紧凑摘要；首页作为可选指标 | 查看模型步骤与状态 | 请求／响应需去重、匹配和定义已完成／进行中；不等同 HTTP 请求计费次数 |
| 已记录 Token | Run 摘要，输入／输出明细按需展开；首页可选汇总 | 查看每次模型调用的用量及原始记录 | 有响应 usage／usage_metadata，需归一化、去重、覆盖率和汇总 |
| 本轮运行时长 | Run 摘要 | 聚焦整个时间范围 | 必须明确来源时间跨度还是采集会话墙钟时长；不能混用服务器接收时间 |
| 工具调用 | Run 摘要：次数，失败／进行中小字说明 | 切换到工具执行列表 | 已有 tool_call_count、配对与工具结果；缺少返回时不能标成功 |
| 最慢步骤 | 摘要旁的小入口或排序选项 | 选中并聚焦可靠 duration 最大的步骤 | 现有 duration 可支持；缺少耗时不按 0 排序 |
| 任务检查结果 | 保留现有独立状态；面板增加检查明细入口 | 查看失败检查和依据 | 已有 outcomes；能数清单时展示通过项／总项；不能用记录条数猜实际断言数 |
| 采集质量 | 现有 Capture 状态旁简短说明 | 查看缺少返回、丢失、缺少用量等明细 | 已有 capture、pairs、warnings；传输完整不等于覆盖 Agent 全部内部操作 |
| 估算费用 | 价格配置可靠后再加，可作为可选摘要 | 显示模型、计价版本、币种、输入／输出项 | 暂无统一计价；代理价格不能直接套模型官方定价；未知显示未配置 |

首轮建议首页最多四项：当前运行、当前待处理、选定范围运行量、选定范围已记录 Token。前两项标“当前”，后两项跟随时间范围。用量缺失较多时，第四项优先展示“用量采集覆盖”，避免误导。

Run 页只增加一条紧凑摘要：本轮时长、模型调用、工具执行、已记录 Token。任务结果、诊断和 Capture 延续现有独立状态，不重复变成四张大卡片。Token 输入／输出拆分可在弹出明细中展示，摘要本身控制高度。

指标块可采用用户提到的“小卡片”，但每块必须回答问题并能进入相关记录。使用白底、轻分隔、清晰数字和标签，不需要彩色大底、渐变、环形仪表或每块一张大白框。

## 5. 真实数据可行性

只读检查两次真实 EnterpriseOps Run 的 LLM 响应：

| Run | 记录到的模型调用 | 输入 Token | 输出 Token | 总 Token | 响应用量覆盖 |
| --- | ---: | ---: | ---: | ---: | --- |
| 7af4add942c044849cef8bc07ad8e6d2 | 5 | 22,126 | 998 | 23,124 | 5/5 |
| 25306a1934194c62bdd14fff81b1a491 | 7 | 40,413 | 1,035 | 41,448 | 7/7 |

数值来自 `output.usage_metadata`，只统计响应，不重复统计请求。这证明“本轮已记录 Token”有实际数据基础；不能据这两次测试声称所有框架、重试、流式调用或模型服务都已完整采集。

“7/7 响应带用量”不代表整个 Agent 的潜在模型操作全部被捕获。数据覆盖的分母始终是已观察到的调用／响应，不能暗示全局全覆盖。

## 6. 指标语义必须先确定

- 区分 Agent 的模型用量和平台 RCA 分析用量。Diagnosis 的 usage 单独记账，不能计入 Agent 本轮 Token。
- 支持 OpenAI 的 prompt/completion 与 LangChain 的 input/output 等字段；保留来源路径和原始证据。不修改原记录，增加读模型或归一化投影。
- 输入、输出合计与来源 total 不一致时保留差异并提示；cached/reasoning 等明细通常属于子项，不能未经提供方定义再次加进总数。
- 同一底层调用可能被多个包装层记录，可靠去重依据来自 correlation／source／producer；无依据不猜。包装层 invoke 数不保证等于底层 HTTP 重试数。
- 没有 usage 显示“未采集”；部分有 usage 显示“已记录 X，覆盖 Y/Z”；运行中标“截至目前”，响应结束后才有用量不伪装成逐 Token 直播。
- 运行中步骤和未知工具结果不要纳入成功率分母；进程失败率、任务检查未通过率、工具错误率和诊断作业失败率分开定义。
- 任务通过率若展示，分母为有明确检查结果的 Run；同时展示未知数量与已检查占比，不能隐藏未检查样本。
- 传输 integrity 独立保留，另行说明语义采集范围。数据完整收到不代表接入了所有 SDK／工具。
- 默认统计真实实时运行，演示明确排除；历史导入单独筛选。来源 origin 和 sample_kind 是两个轴。时间趋势使用可解释的来源时间，不把导入时刻当历史 Agent 实际执行时刻。
- 首页当前状态计数和选定时间窗口累计值分别标明范围；所有图与下方结果共享查询条件，不静默忽略筛选。
- 少量样本先展示原始数量和分布；p95、百分比和同比必须标样本量，不能用两次实验给出稳定性结论。无样本／无字段不是 0。
- 模型和工具可能并发或嵌套，耗时不能直接相加成“占总耗时百分比”；当前优先最慢步骤排序，暂不做误导的时间分解饼图。

## 7. 更能改善日常使用的交互

### 首页

首次使用保留接入命令、平台等待状态和演示；已有真实记录时使用紧凑的“开始监控”入口，正在运行及待处理 Run 仍是主体。选择接入方式后明确说明可采集工具、模型还是仅进程／日志，不能给出“任意 Agent 一行命令就全部监控”的承诺。

增加接入反馈：收到第一条事件、已收到工具调用、已收到模型用量、尚无任务检查记录。比抽象的“连接成功”更有用，不需要新增业务对象。

首页趋势条后续采用“图中发现异常 → 点击筛选列表”的模式，而不是只加一张无法操作的折线图。当前测试数据少时，紧凑概览优先，趋势显示真实空档，不填造平滑曲线。

### Run Workspace

保留左侧时间轴、右侧选中详情、下方 Run 面板。增加用量摘要及每次模型输入／输出 Token、模型、真实延迟。可提供按耗时或用量找步骤的入口，但共享时间轴仍保留来源顺序，排序视图不能悄悄改变时间含义。

新增“执行步骤”查看预设：突出有可靠关联的工具执行及模型边界；LOG 继续在“全部事件”可访问。LLM 只有唯一关联、明确起止与有效时间才可聚合为完整条形；不能因为想展示 Token 就把所有 LLM 响应画成长条。

补充上下方向键选择步骤、明确焦点、分栏宽度调整、选中事件链接和筛选记忆。已有 zoom／fit／聚焦、定位失败、证据反向定位、dock 高度调整继续复用。键盘快捷键不得抢输入框编辑；分享能力先称“本地定位链接”，本机回环 URL 不代表成员在另一台机器可直接访问。

实时新数据到来只短暂提示新增数量；用户正在读旧事件时保持暂停跟随，提供恢复按钮。用量响应结束后更新数字，不制造流式打字效果或一直闪烁的统计卡片。

### RCA 与任务检查

RCA 当前已经在 Trace Toolbar 有主入口，不再宣称它藏在技术详情。下一步重点是行动状态：未分析时“分析失败原因”，定位后“预览并分析原因”，已有报告时“查看原因分析”；已存在逻辑可继续精简解释。

失败时显示紧凑事实，分析后呈现“可能原因 → 对应证据 → 下一步检查”；保持引用点击选中轨迹，不把 RCA 改成一个聊天窗口。完整报告仍按需展开。无工具但检查失败时，明确说明本次证据是否支持定位，不把按钮禁用原因只写成 HGT 术语。

任务检查解释为“测试／规则是否通过”，简洁展示来源、依据、失败项。已通过且没有原因分析的 Run 可收起不必要的下方面板；失败、有新报告或检查冲突时强调相关入口，不自动发起诊断。

### Task 历程

保留多轮历史职责。可比较前后两轮检查结果、可靠时长、调用数、Token 变化；不能因后一轮通过就声称前一轮 RCA 被证实。不同模型／参数／检查集需要明确标注，否则用量差异不等于效率改善。

## 8. 局部视觉规范建议

- 主要操作、步骤名称及结果优先约 14–15px，核心摘要数字约 22–26px；辅助说明约 12–13px。原始代码／日志保留等宽字体和合理行高，依据 1366×768 实际阅读校验，而非一律放大。
- 保留纯白基础背景。层级来自字号、密度、间距、固定区域和选择状态，减少重复标题／说明段。
- 类型色用于条、轻量标签；失败红色、成功小型绿标、running 文本／状态、未知中性；选择状态不覆盖失败语义。不能把大 Token 数自动刷红，没有预算阈值时它只是用量。
- 图表标单位、时间区间、样本数、覆盖率；不为每项都加装饰性 sparkline。重要信息至少有文本／形状辅助，不只靠颜色。
- 加载不闪清已有指标，刷新失败保留旧值并标更新时间；区分首次为空、筛选为空、无时间字段、未采集用量。

## 9. 建议顺序与组件范围

| 顺序 | 工作 | 涉及范围 | 验收重点 |
| --- | --- | --- | --- |
| 1 | 用量归一化与调用计数定义 | 采集记录读模型／后端投影，api.ts 类型 | 真实 7 次调用不计成 14；得到 41,448；未知不显示 0；RCA 用量隔离 |
| 2 | Run 紧凑摘要与模型详情 | run-workspace.tsx、局部 CSS、可复用指标摘要组件 | 点击数字能定位对应步骤；保留 Trace 空间与四类状态 |
| 3 | 首页轻量概览与接入反馈 | main.tsx HomePage、workbench.py 全量聚合查询 | 超过 20 条仍计数正确；当前／时间窗口不同口径明确；演示与导入可区分 |
| 4 | 调查效率与可读性 | Trace 查看预设、键盘／焦点、分栏、run-panels | 原始证据不丢失；实时不抢阅读；禁用理由可理解；1366 宽度无挤压 |
| 5 | 真实用量趋势、可靠计价、前后对照 | 聚合 API、价格配置、ComparePage | 相同筛选同一范围；成本为估算；未配置价不计 0；比较注明条件差异 |

暂缓：任意拖拽 Dashboard、网络吞吐／CPU／GPU 卡片、TTFT／输出 Token 每秒、预算自动阻断、自动模型诊断、根因准确率／置信度百分比、复杂 Agent Graph。当前缺少必要采集或评测基础，不是换一种 UI 就能成立。
