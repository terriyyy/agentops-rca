# 第一版开发计划

状态：planned，尚未开始产品实现。范围基于已核实的历史记录，而非申报书中的全部技术设想。

## 1. 目标与交付边界

第一版面向单用户、单项目、本地代码／运维 Agent。用户导入一次任务的两轮记录后，可以回答：任务要做什么、每轮发生了什么、诊断依据在哪里、第二轮是否通过验收。

分成三个独立验收点：

| 里程碑 | 可交付能力 | 发布条件 |
|---|---|---|
| V0.1 历史记录工作台 | 导入、任务／执行列表、轨迹详情、历史诊断、证据跳转、两轮对照 | 不依赖 HGT 或付费 LLM，样例与状态语义验证通过 |
| V0.2 实际诊断 | 在隔离进程中调用固定版本 AgentTether，保存新诊断与模型能力状态 | 真权重及依赖加载通过；诊断来源、失败／超时可审计 |
| V0.3 受控现场闭环 | 一种本地 Agent 的现场采集、一次指导重试和独立验收 | 仅限可恢复实验任务，保存新的 Run 和验收证据 |

本轮仅交付上述规划和 Git 基线。以前方案将在线采集、系统关联与修复纳入整体 MVP；现在将首个可演示版本收窄到 V0.1，并不把历史成功案例宣称为新平台已经自动修复。

## 2. 当前证据基础

- 代码样例 `sympy__sympy-13031`：两轮 784/567 条事件，334/241 对调用返回；保存的验收历史分别为 unresolved/resolved。适合作为 V0.1 主样例。
- 增强版 `banking_knowledge/task_071`：可补充图、恢复记忆和干预记录；仍属于补充场景，不改变代码／运维的主定位。
- 已找到与发布包 LFS 目标哈希完全相同的权重；本地补齐和实际加载尚未完成。
- 历史增强报告存在 HGT 依赖加载失败。该样例只能证明记录存在，不能证明完整模型已经运行。
- 原始 grader 完整报告不一定随案例保存；UI 应表明“导入的历史验收”，不能写“平台重跑验证通过”。

## 3. 模块边界

| 模块 | 负责 | 首版边界 |
|---|---|---|
| Importer | 接收明确列出的样例包文件、校验大小和格式、登记来源与哈希 | 不扫描任意服务器目录，不执行导入文件中的命令 |
| Normalizer | 适配旧 PROBE、增强版报告及 JSONL；规范化任务／轮次／事件 | 保留原字段及质量告警；不能静默修正未知语义 |
| Storage / API | 元数据、事件查询、附件保存、分页、导入状态 | 单机本地存储；按事务完成一轮导入 |
| Correlator | 在同一 Run 内建立调用返回及报告证据引用 | 精确 ID 优先；无法确认的关联标为未解析 |
| Diagnosis adapter | 统一历史报告输出；V0.2 增加 AgentTether worker | 历史与重新诊断分开；报告内容是数据 |
| Outcome adapter | 保存评测来源、结果、评价依据及冲突 | 不以进程退出码或报告 ok 代替任务验收 |
| Frontend | 任务列表、详情、两轮对照、证据面板、能力状态 | 后端 API 驱动，不另写一套诊断逻辑 |

AgentTether 已有采集能力，后续优先复用。PROBE 是算法／历史格式名称，通用工程采集能力统一称 Collector，不单独复制一个“PROBE 前置模块”。

## 4. 实现形态与目录草案

建议沿用 Python API、TypeScript 前端。V0.1 先用 SQLite 和本地 artifact 目录，减少演示环境依赖；此前 PostgreSQL/JSONB 方案留待确有并发与部署需求时引入。第一轮实现时锁定具体依赖版本并提交锁文件，不预先堆叠队列、图数据库或微服务。

```text
apps/
  api/                    # Python API、导入与查询
  web/                    # TypeScript 页面
packages/
  contracts/              # 数据契约、枚举、版本化 JSON Schema
  adapters/               # 历史格式与 AgentTether 对接
tests/
  fixtures/               # 审查后的小型脱敏数据
  integration/            # 导入、持久化、证据引用和状态语义
docs/
data/                     # 本机数据，忽略
artifacts/                # 本机原始附件，忽略
```

这些是后续拟建目录，当前不生成空壳业务代码。V0.2 worker 使用独立进程；V0.1 无需先做通用任务调度中心。

## 5. 页面信息架构

1. `/tasks`：任务名称、任务验收状态、执行次数、最新诊断来源；导入入口。
2. `/tasks/:taskId`：任务目标、各轮概览、按明确验收依据显示前后变化。
3. `/runs/:runId`：概览、轨迹、诊断、验收四个标签；证据抽屉显示原文件与行号。
4. `/tasks/:taskId/compare`：选择两轮，对照验收结果、关键错误、诊断与反馈；默认不做全文大规模 diff。
5. 导入结果页／面板：格式、重复导入结果、告警、失败原因；不把缺报告视为整条轨迹不可看。

图视图是诊断详情中的可选视图；旧报告无图时显示“来源未提供”。模型不可用、历史导入、未独立验证必须可见。

## 6. 阶段与验收标准

### P0：样例与数据契约

产出：脱敏样例清单、源文件哈希、适配版本、任务和轮次映射、核心 Schema。

验收：同一任务得到两个 Run；保留原 attempt=0；轮次从清单／目录元数据读取并记录来源；任务验收依据与 report.ok 冲突可表达；样例不含凭据、机器地址或未经审查的完整评测答案。没有再分发许可时只保留本地私有原件，仓库使用审查后的最小派生夹具。

### P1：后端导入与持久化

产出：最小 API、数据库迁移、文件存储、两种历史报告适配器、导入记录。

拟定接口：`POST /imports`、`GET /imports/:id`、`GET /tasks`、`GET /tasks/:id`、`GET /runs/:id/events`、`GET /runs/:id/diagnoses`、`GET /evidence/:id`。可使用明确文件列表的 multipart 导入，首版无需支持任意压缩格式。

验收：重启后数据可读；重复导入不重复生成 Run；格式错误、超限文件和路径穿越被拒绝；单轮导入失败不残留半条可见记录；分页稳定；原文件不能通过接口任意路径读取。

### P2：前端纵向闭环

产出：上述列表、详情、对照和证据面板，连接真实 API。

验收：可从任务进入两轮执行，并从诊断定位到原始事件；展示 Submitted 与 unresolved/resolved 的区别；无图、无报告、缺验收有明确空态；不直接执行日志中的 HTML／脚本；大段输出折叠且可查看原文。

### P3：V0.1 联调与交付

产出：完整主样例回放、关键自动化检查、最短启动与演示说明。

验收重点：正常配对、缺返回、重复导入、attempt 冲突、验收冲突、未解析证据、跨 Run 同名 correlation_id、数据缺失。端到端检查至少覆盖导入→两轮对照→证据跳转。无需为静态文档和简单 UI 文案编写镜像式测试。

退出条件：新环境按说明可启动；主样例导入成功且结果来源清楚；不需要真实模型密钥就能完成 V0.1 演示。

### P4：V0.2 AgentTether 诊断接入

产出：权重校验、依赖固定、独立进程 adapter、能力检查、诊断作业和超时取消。

顺序：校验真实权重→依赖导入及模型加载→无网络结构链路→配置获准使用的模型服务→一个失败案例的实际诊断→前端展示与来源检查。

验收：记录算法版本、输入快照、权重哈希和报告版本；明确 ready/degraded/unavailable；模型加载失败不会伪装成完整 RCA；不覆盖历史报告；模型请求前确认当前任务授权与费用边界。CPU/GPU 与依赖兼容性以加载结果为准，不假设 GPU 必需。

### P5：V0.3 现场采集与一次重试

产出：一种串行 Agent 的采集接入、Run 生命周期、独立验收器和指导重试。

验收：真实新运行产生新 Run；任务成功由独立测试确认；重试保留父 Run／指导来源；只支持预定义、可恢复实验任务。此后再决定是否增加 PID／文件等系统采集和跨层关联。

开发顺序为 P0 → P1 → P2 → P3；P4 的环境验证可在数据契约稳定后独立推进，不阻塞 V0.1。P5 依赖 P4 验收。按验收关口安排任务，不在团队工时未知时承诺固定日期。

## 7. Correlator 的首版规则

- 连接键必须带 Run 命名空间；同名 ID 跨轮不能相连。
- tool_call 与 tool_return 使用 correlation_id；重复键不任选一条，保存歧义。
- parent_span_id 仅在源记录确实提供时生成父子边。
- 报告引用按原始 event/span ID、TU 映射或文件行号解析；没有可验证映射就标记 unresolved。
- 时间相近仅作展示排序，不能标记为因果或确定归属。
- 不因工具返回缺失丢掉 tool_call；不静默把并行记录压成串行因果链。
- `bash` 与 `subprocess.run` 等不同层级记录均保留；未确认重复关系前不自动删除。

## 8. 现在做与推迟项

现在做：样例审查、契约、导入适配、持久化、证据引用、任务验收语义、纵向页面、Git 与运行说明。

稍后做：权重落地和实际模型诊断，作为 V0.2 独立验收；再做现场采集与受控重试。

推迟：多租户／权限系统、任意 Agent 框架支持、全面 eBPF/系统探针、实时分布式追踪、图数据库、自动执行修复建议、大规模训练、性能效果论文评测、云部署和 Kubernetes。

## 9. 风险与处理

| 风险 | 处理 |
|---|---|
| 历史格式与发布代码不同 | adapter_version 与 source_algorithm 分开记录，保留原文 |
| 结果状态互相冲突 | 每条 OutcomeEvidence 保存来源、时间、依据，不取“任意一条成功” |
| 日志含个人信息／评测答案 | 本地原件隔离；最小脱敏夹具；在线输入与 grader 答案分开 |
| 重复采集使计数虚高 | 区分采集层级与工具决策，先保留再聚合 |
| HGT 环境不可用 | capability 状态透明，V0.1 不依赖模型 |
| 历史配对集合有选择偏差 | 只用于功能验证，不能据此宣称恢复成功率 |
| 改名／换机器使绝对路径失效 | 仓库内相对引用；本地配置管理外部目录 |
