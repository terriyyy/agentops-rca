# 当前项目缺口与三人分工建议

2026-10-02。依据当前工作区代码及真实验收，不修改产品。本文件是供团队讨论的建议，不表示已批准自动修复/模型调用/服务器部署。

## 当前定位

V0.4 的本地 Run 调试工作台，加上真实 Agent 采集桥接的原型。观察和显式诊断链路已有实现；接入产品化、跨任务 RCA 评测和平台驱动的修复验证尚未完成。不能给“完成百分比”：界面功能实现、接入覆盖、诊断准确率及部署可靠性是不同维度。

真实桥接验收：同一个 EnterpriseOps 邮箱案例两轮；第一轮10/14检查通过，反馈第二轮14/14；12模型请求，17组工具配对，308采集事件。原Agent反馈逻辑推动第二轮；平台未把RCA建议注入Agent，不以通过证明RCA修复有效。见 agenttether-real-agent-replay.md。

| 方面 | 已有 | 欠缺/应验收 |
|---|---|---|

| 语义采集 | @tool；显式 AgentTether OpenAI/AsyncOpenAI、LangChain代理、MCP/HTTPX包装；EnterpriseOps适配 | 需指定目标/保存代理，有侵入成本；版本覆盖有限；真实事件与覆盖能力分开展示、避免重复层采集、未知/不支持明确提示 |
| 流式 | SSE实时事件更新、请求/完整响应 | token/chunk消费、提前关闭/取消等完整流式生命周期；模型区间 UI 当前仍未投影 |
| Trace | 工具配对、可信时间区间、真实parent、搜索/筛选/选中详情/证据 | 日志淹没工具、长轨迹分页、事件覆盖解释、失败检查与全成功工具共存的入口 |

| 团队交接 | 私有算法/权重分发文档、普通成员无权重开发 | 最新桥接/实测说明仍未提交；需固定交接commit、分支与接口契约，真实遥测/凭据不进Git，旧文档pending需更新 |

## 推荐产品验收目标

对明确支持的一种本地Python Agent：一次配置，后续一条命令；网页实时看工具/模型/失败，结束后手动HGT和预览确认RCA；实际证据解释可能原因；用户在本地确认变更或反馈并复跑；平台关联前后Run，依据独立检查评估变化。平台后端不执行用户任意命令，不自动付费，不把假设当真相。

这一目标比“兼容所有Agent/自动修复一切”可验证。EnterpriseOps邮箱案例补充集成证明，但本地代码/运维Agent仍是首要目标场景，需要真实文件操作/测试/修复案例。

## 三人分工（按能力可对调）

### 成员A：采集与接入产品化

负责 packages/collector、SDK兼容测试、最小接入示例。统一显式profile/配置与CLI入口，支持OpenAI或LangChain一种主要入口，保留process-only降级；doctor预检、自动Run链接、能力声明；再做模型流式/断连/取消。EnterpriseOps适配作为参考，避免继续堆宿主专用脚本。

首两天：独立环境跑通无模型自检，写支持版本/捕获范围；交付一次配置后的最小命令和失败/未知/取消测试。后续真实Agent：调用数、返回数、工具参数与结果对照、重传不重复、凭据不泄露。不以只看到stdout为完整语义接入通过。

### 成员B：RCA评测与算法适配

负责诊断worker、候选/上下文接口、评测数据和评测脚本，使用受控私有权重环境。先固定原算法基线，不直接重训；设计10–20个初步失败案例/配对成功轨迹及独立根因标注，涵盖工具异常、参数/路径错误、超时、状态污染、所有工具成功但任务失败。区分标注依据与推理可见输入。

首两天：失败类型/数据格式/评测脚本草案、3个已人工核对案例跑通HGT基线，不要求两天做完大规模评测。后续测Top-k根因步骤命中、无故障误报、候选证据充分性、RCA描述正确性、token/时延成本与不确定性。语义不足时补上下文；比较LLM-only与HGT+LLM作受控实验，非生产自动模型调用。超参数/提示/权重更换单变量、有版本、独立测试集，防验收答案泄漏。

### 负责人：验证闭环、体验与集成

负责用户流程、Run/Task前后关系、API协调、团队发布。先给“人工确认修复→本地复跑→独立检查”闭环，不做全自动repair。把诊断建议与实际行动分别记录，引用来源诊断/之前Run，不根据相邻轮次推断因果。复用现有Task/Run/Feedback概念，不预设新增大型实体。

首两天：固定交接版本/任务单/接口，整理一个本地代码Agent失败→诊断→人工最小修复→复跑案例，定义怎样证明假设/怎样证明仅任务通过；让两位未熟悉项目的人实测首用路径，记录误解。后续做日志密度/模型输入输出/检查expected-actual可读性、未覆盖说明、时间/状态单位一致性、实验演示。

## 协作边界与共同验收

- 各自feature分支；Collector核心由A负责，诊断核心由B负责，公共Schema/API/前端由负责人集成。capture扩展字段、模型phase/ID、诊断引用、复跑关系改变先统一契约。
- A不需权重；B通过受控算法目录/226集成环境获取权重，不把秘密推到Git。每人私有.env和独立数据库，不共用记录库开发。
- 一条共同失败case贯穿采集→诊断→行动→复验；首次成功不说明算法泛化，20个案例也只是初步研究。
- 最近未提交改动先审查后固定commit再交接；本次用户未请求Git操作，当前未执行提交/推送。

## 优先级

先做：固定目标Agent和验收样例；可复现团队交接；受支持profile的一命令接入；根因标注与RCA基线；人工修复复验闭环；初用可理解性。

随后：逐token流/模型Span；文件/代码diff信号；更多失败类型与跨工具评测；长轨迹/长断连；稳定226集成实例。

延期：全自动改代码/执行任意命令；所有框架兼容；没有评测依据的重训；多租户SaaS/复杂微服务；再度整页重构/纯视觉打磨。延期不等于永久不做，按项目申报验收要求决定。
